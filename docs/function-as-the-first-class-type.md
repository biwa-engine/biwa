# 関数を第一級の型にする (function as the first-class type)

GitHub issue #7 「[feature] Function as the first class data type (pass to function argument,
struct member, etc...)」(labels: enhancement, compiler) を受けて、目指すゴールをまとめる。
UI API の Phase3 (`Button.on_click: fn(Event)`、`Window.on_event`、`docs/ui-api.md`) の前提でもある。

## ゴール

関数を値として扱えるようにする。具体的には次がすべて書けて、型検査を通り、
wasm (tier 1) で正しく動くこと。

1. 関数の型を書ける (型表現)
2. 名前付き関数を値として参照できる (`let f = add;`)
3. 関数を関数の引数・戻り値にできる (高階関数)
4. 関数をユーザ定義データ型 (struct のメンバ、enum のペイロード) に持てる
5. 関数リテラル (無名関数) を書ける
6. 関数型の値を呼べる (`f(1, 2)`、`self.handler(e)`)

## 構文 (issue #7 より)

### 型表現

```biwa
fn(Int, Foo) -> Bar     // 引数 Int, Foo を取り Bar を返す
fn(Int)                 // 戻り値が Void
fn[T, U](Int, T) -> U   // ジェネリックな関数の型
```

> 決定事項 (下記「多相性」) により、`fn[T, U](..)` のように**型の中に量化子を持つ関数型は書けない**
> (rank 2 以上になるため)。ジェネリックにしたい場合は、それを使う定義の側のジェネリック引数か、
> ジェネリックな型エイリアス (`type Mapper[T, U] = fn(T) -> U;`) を使う。

### 関数リテラル

```biwa
fn(x, y) { x + y }                         // 引数・戻り値の型は推論する
fn(x: Int, y: Foo) -> Bar { y.bar(x) }     // 注釈も書ける
fn[T, U](x, y: T) -> U { x.foo(y) }        // ジェネリック
```

### 使用例 (目標)

```biwa
struct Button {
  label: String,
  on_click: fn(Event),
}

fn apply_twice(f: fn(Int) -> Int, x: Int) -> Int {
  f(f(x))
}

fn add_one(x: Int) -> Int { x + 1 }

let y = apply_twice(add_one, 3);            // 名前付き関数を値として渡す
let z = apply_twice(fn(x) { x * 2 }, 3);    // 関数リテラル
```

## 方針 (決まっていること)

- **クロージャは当面サポートしない** (issue #7 のコメント)。可変性の安全性を検査するのが難しいため。
  - したがって関数リテラルは**外側の局所変数を捕捉できない**。捕捉しようとしたらコンパイルエラーにする
    (「クロージャは未対応」と名指しする)。
  - 将来クロージャを入れる場合も、関数型 `fn(A, B) -> C` は純粋な関数とクロージャの両方を許す
    (他の GC 言語と同じ)。Biwa は可変性・ライフタイムの検査によるメモリ安全は保証せず、
    **型安全だけを保証する**。Rust 風の `Fn` / `FnMut` / `FnOnce` の区別はしない。
  - そのため、今の段階で関数型の値の表現を「捕捉なしの関数への参照」に決め打ちしすぎず、
    後でクロージャ (関数 + 捕捉環境) に広げられる余地を残す。

## 決定事項 (目指す形)

### 呼び出しは「式 + 引数列」、関数型の値なら呼べる

- `<式> ( <引数列> )` は**関数呼び出し**とし、`<式>` の型が関数型なら呼べる (型推論で決まる)。
  呼び先は名前 (パス) に限らない: struct のメンバ (`self.on_click(e)`)、関数を返す呼び出しの結果
  (`make_handler()(e)`) なども呼べる。
- struct の**関数型のメンバの名前は、型の関連アイテムと同じ名前にできない** (衝突は名前解決でエラー)。
  これで `x.bar(..)` は、`x` の型が分かった時点で「メンバ `bar` (関数型) の値の呼び出し」か
  「メソッド `bar` の呼び出し」かに一意に決まる。`<式> . <identifier>` は `<式>` の型を知らないと解けないので、
  決めるのは型推論の段である (名前解決をできるだけ先に済ませ、ここだけを型推論に任せる biwac の方針どおり)。
  - 当初は全メンバを関連アイテムと同じ名前空間で一意にする予定だったが、std の UI 要素のビルダー
    (メンバ `width` とメソッド `width(self, ..)`) やゲッター (メンバ `x` と `fn x(self)`) がすべて衝突するため、
    **関数型のメンバだけ**に絞った。関数型でないメンバは `x.bar(..)` の呼び先になり得ないので、
    関連アイテムと同じ名前でも曖昧さは生じない (`x.bar` は常にメンバ、`x.bar(..)` はメソッド)。

### 関連アイテムの同名が許される場合

名前ツリーは 1 つの名前空間だが、「名前だけで見たとき」重複しているように見えても許される例外がある。

- 固有の impl (`impl Type[T1, T2, ..] { .. }`): 具体の `T1, T2, ..` の組が衝突し得ない impl どうしなら、
  同名の関連アイテムを持てる。ただし固有の impl は**その型が定義されたのと同じパッケージ**でなければならず、
  型パラメータに自パッケージの型が含まれていても、他パッケージの型への固有の impl は認めない。
- trait impl (`impl Type: Trait[T1, T2, ..] { .. }`): 具体の `T1, T2, ..` の組が衝突し得ないなら実装でき、
  結果として同名の関連アイテムを持ち得る。ただし `Type` か `Trait` のいずれかが自パッケージで定義されて
  いなければならない (Rust の orphan rule を簡略化し、許容範囲を狭めたもの)。

### メソッドは「第一引数が `self` の関連関数」に統一する

- `fn bar(self, a: A) -> B` (impl の中) は、第一引数が `self` である特殊な**関連関数**として扱う。
  これにより `Foo::bar` が `fn(Foo, A) -> B` 型の値として使える。`x.bar(a)` は `Foo::bar(x, a)` の糖衣になる
  (ただし `x` の型が分かるまで `bar` がどの関連関数かは決まらないので、糖衣を剥がすのは型推論で呼び先が決まった後)。
- ただし**メソッドを値として渡すときは `Foo::bar` (親の型の関連関数) の形だけ**を許す。
  `x.bar` / `self.bar` のように `self` (受け手) を含んだまま値にするのは、実質的にクロージャなので許さない。

### 関数値の等価比較は型エラー

- 関数型の値どうしを `==` / `!=` で比べることはできない。型エラーにする。

### scene は将来関数型として扱う

- 将来的に scene を `type Scene[S] = fn(Game[S]) -> Game[S];` のような関数型として扱いたい。
- そのため関数型の型エイリアス (ジェネリックなものを含む) も正しく機能する必要がある。ただし直ちにではない。

### 多相性は「使う場所で決まる」範囲 (rank 1) に限る

- 単相化 (monomorphization) を採っている以上、多相性はコンパイル時に決定できる範囲に限る。
  ジェネリックな関数を値として使うときは、**使う場所で型引数が決まる**形だけを許す。
- 関数の型の中に量化子を持つ型 (`fn[T](T) -> T` を引数・メンバ・変数の型として書く、
  つまり rank 2 以上) は許さない。rank の区別は impl-status の md を参照。
- rank 2 にしたくなる形の多くは rank 1 に書き直せる: `fn use_twice(f: fn[T](T) -> T)` は
  `fn use_twice[T](f: fn(T) -> T)` とすれば rank 1 になり、基本的にはこれで困らない。
- ジェネリックな無名関数 (`fn[T](x: T) { .. }`) は当面考えない。

### 無名関数が外から参照できるのはグローバルな静的な存在だけ

- 無名関数の本体から参照できるのは、関数・関連関数、将来の `const` によるグローバル定数のような
  **グローバルで静的なもの**だけ。局所変数 (引数・`let`・`self`・scene の `g` や `#let` など) は参照できない
  (捕捉 = クロージャになるため)。参照したらコンパイルエラー。

## シリアライズとの関係

将来、ゲームデータのセーブのために基本的な型をシリアライズ / デシリアライズできるようにしたい。
**関数はその対象にしない** (関数参照はビルドや実行をまたいで同一性を保てず、保存しても意味が無い)。

- シリアライズできる型を表す **marker trait** (例: `Serialize` / `Save`) を導入し、
  関数型はそれを実装しないものとする。関数型をメンバに持つ struct も、自動では実装されない。
- セーブ対象 (例: `Game` の状態 `S`) にはこの trait を境界として要求し、
  関数を含む型をセーブ対象にしようとしたらコンパイルエラーになるようにする。
- marker trait の自動実装 (メンバがすべて実装していれば実装される) の仕組みが要るかどうかは、
  serialize の設計と合わせて決める。少なくとも第一級関数の設計は、
  「関数型は serialize の対象外」と型で区別できる前提で進める。

## 未決事項 (要議論)

- 将来導入するモジュールレベルの変数・定数のうち、無名関数から参照してよいのは不変 (`const`) なものだけにするか。
- trait の関連関数 (`T::guee` など、ジェネリック引数の制限経由のもの) を値として使えるか。

現状の調査結果と実装のステップは `docs/function-as-the-first-class-type-impl-status.md` にある。
