# canvas オブジェクトと遷移 (transition) の syscall

`docs/media-syscall-wasm.md` で挙げた 3 案の検討を受けて、
実際に採る形を決める。前提の実行モデルは `docs/execution-model.md` にある。

## 何を解きたいのか

canvas 上のオブジェクト (画像・将来は動画や GIF) を、
**あり得る限り豊かなアニメーションで**更新したい。
更新は「変更後の状態」と「そこに至る遷移方法」の組で表す。

素直に書くと 1 パラメータあたり `kind`, `value`, `after`, `duration` の 4 値で、
パラメータは `x`, `y`, `w`, `h`, `alpha`, `theta` + 将来の回転 2 軸で 8 つある。
全部を 1 つの syscall で渡すと 32 引数になる。これが出発点の問題である。

## 結論

**設定 (`add_`) と発火 (`start_`) を分ける** (media-syscall-wasm.md の案 2)。
そのうえで以下を決める。

```
// --- 生成・破棄 -------------------------------------------------------
// id は Worker 内で採番して同期に返す (メインスレッドとは往復しない)。
// 拡張子からフォーマットを判定し、画像 / 動画 / GIF の使い分けはエンジンが行う。
fn create_object(
  path: String,
  layer: u32,                          // canvas レイヤーの index
  x: f32, y: f32,                      // 画像の中心の座標 (出力先の Canvas Element の中央が原点, y は上が正)
                                       // canvas の範囲が -50.0..50.0 になる単位 (下記「座標の単位」)
  w: f32, h: f32,                      // 100.0 が canvas の幅 / 高さ。負なら「指定しない」
  alpha: i32,                          // 0-255
  theta: f32,                          // 度。回転の中心は画像の中心
) -> u32;

fn delete_object(id: u32, after: u32);

// --- 遷移 -------------------------------------------------------------
// add_ は「次の start_ で発火する集合」に積むだけで、何も起こさない。
// 値は val_i (i32) と val_f (f32) の 2 枠で渡し、使わない方は 0 で埋める
// (`sys_ui_set_property` と同じ運用)。alpha は val_i、x / y / w / h / theta は val_f を使う。
fn add_transition(
  id: u32, param: u32, kind: u32, val_i: i32, val_f: f32, after: u32, duration: u32,
);

// 積まれていたものを発火する。オブジェクトを跨いで一斉に始まる。
// sync については「スケジューリング」を参照。
fn start_transitions(sync: u32);

// --- 待つ -------------------------------------------------------------
// sync 印の付いた遷移がすべて終わるまでシーンを止める (ブロッキング)。
fn await_transitions();
fn sleep(ms: u32);
```

引数は最大 8 個に収まり、パラメータ数にもオブジェクト数にも上限が無い。

### 座標の単位

x / y / w / h は出力先の Canvas を基準にした単位で、syscall には f32 で渡す。

- x / y は **canvas の範囲が -50.0 から 50.0** になる (x は canvas の幅、y は canvas の高さの 1/100 が 1)。
- w / h は 100.0 が canvas の幅 / 高さ。負なら「指定しない」で、片方だけ負なら
  画像の縦横比を保つように (一度 px に直して比を取る)、両方負なら画像の元の大きさ (px) で
  エンジンが決める。決めるのは最初に描画先の大きさが分かったときの 1 回で、以降は canvas の単位の値になる。
- エンジンは射影のときに描画先の今の大きさで px に直すので、canvas の大きさが変われば中身も追従する。
- std では `std::game::canvas` の `Cx` / `Cy` / `Cw` / `Ch` で扱う。

## 実装の順序

**wasm ターゲットが tier 1、TypeScript ターゲットが tier 2 である。**

設計の判断が両者で割れたときは wasm を優先する。
`alloc` の採番、`start_` を明示する理由、cast のまとめ流しは、
いずれも wasm の輸送路から出てきた要求である。

TypeScript ターゲットでは中断しない syscall はただの関数呼び出しなので、
輸送路まわりの仕掛けは何も要らない。**同じ `api/*` を呼べばそのまま動く**。
`vm/handlers.ts` と std の `[[native(arch="typescript")]]` を後から埋める。

## 設計判断

### 案 3 (wasm の構造体をホストが触る) は今は実装できない

**WasmGC の struct は JS から中身を読む手段が無い。** 参照は不透明で、
フィールドを覗くリフレクション API が無い。

linear memory 経由なら可能ではある (`worker.ts` の `string_const` が実際にそうしている)
が、それも **Worker のメモリ**である。`host.ts` はメインスレッドに居るので、
`shared` でない memory は覗けない。したがって案 3 を通すなら

1. biwac にスクラッチ領域とアロケータを用意させる
   (今 memory にあるのは文字列リテラルのデータセグメントだけ)
2. Worker 側でデコードしてからメインへ cast する

の 2 段構えになる。コンパイラを巻き込む割に、得られるものは
「1 回の postMessage にまとまる」だけで、それは後述の cast のまとめ流しで
API を歪めずに手に入る。

案 1 (n パラメータ版 syscall) は案 2 の劣化版である。引数は大して減らず、
同時発行できるパラメータ数に構造的な上限が入る。

### id はエンジンが割り当てるが、往復はしない

`create_object` は id を返す。ロードの成否は返さない
(非同期ロードなので `create` の時点では確定しない)。
biwa 側からロード失敗に対してできることは無いので、
エンジンがログを出すか panic するかはエンジンの実装の選択でよい。

問題は wasm で戻り値のある syscall をどう作るかである。
素朴にやると `call` (`Atomics.wait` でメインスレッドと往復) になり、
画像を出すたびにスレッドが止まる。

**採番を Worker 側でやれば往復は要らない。**
`contract.ts` の区分に 1 つ足す:

| 区分        | 実行される場所                  | 戻り値                 |
| ----------- | ------------------------------- | ---------------------- |
| `local`     | Worker                          | あり (Worker 内で完結) |
| `cast`      | Main                            | なし                   |
| `call`      | Main                            | あり (Worker を止める) |
| **`alloc`** | **Main (本体) + Worker (採番)** | **あり (止めない)**    |

`alloc` は「Worker 内のカウンタから新しい id を採り、それを含めて
メインスレッドへ cast し、id を同期に返す」。wasm から見れば
「戻り値のある、止まらないホスト関数呼び出し」になる。
カウンタは単調増加で決定的なので、後述のセーブ・ロードとも噛み合う。

TypeScript ターゲットでは中断しない syscall はただの関数呼び出しなので、
エンジン側の同じカウンタから返すだけでよい。

### create も object に統一する

`update` / `delete` / 遷移がメディア種別に依存しない以上、
`create` だけ `create_image` / `create_video` に割れているのは筋が悪い。
**拡張子からフォーマットを判定し、Sprite / ビデオテクスチャ / AnimatedSprite の
使い分けはエンジンが引き受ける。**

遷移の機構は「数値パラメータを持つ表示オブジェクト」に対して書くので、
バックエンドが何であっても同じものが動く。

### layer は整数の index

背景・立ち絵・前景といった意味づけは std の仕事で、
プリミティブには**レイヤーの index だけ**を渡す。

出力先の Canvas Element ごとの描画先が index を受けて canvas レイヤーを必要に応じて作る
(`CanvasSurface.layer(index)`、`engine/canvas/CanvasSurfaces.ts`)。**レイヤーは安いので、たくさん使ってよい。**
そのため同一レイヤー内の z 順は「作られた順」で足り、
`set_z` のようなものは要らない。細かく前後を制御したければレイヤーを分ける。

### `add_` だけでよい。`start_` が入れ替える

`set_` か `add_` かで迷う必要は無い。**両方の意味は `start_` が担う。**

**リストはオブジェクトごとに 2 本持つ。**

```
CanvasObject
  active   : param ごとの、今走っている区間列
  pending  : param ごとの、次の start_ のために積まれている区間列
```

- `add_transition(id, ...)` は、そのオブジェクトの `pending` に積むだけで何も起こさない
- `start_transitions(sync)` は、**`pending` が空でない全オブジェクト**について
  `pending` を `active` へ移し、`pending` を空にする

**発火の引き金だけがオブジェクトを跨ぐ。** データはオブジェクトの中にある。
跨がせるのは、複数のオブジェクトを揃えて動かすため
(全員が一斉に画面外へ滑る、など) である。オブジェクトごとに `start_` を分けると、
wasm では別々のメッセージになってフレームを跨ぎうるので、揃う保証が無くなる。

「このオブジェクトだけ始めたい」は `add_` をそのオブジェクトにしか出さなければ
そうなるので、**`start_transitions_of(id)` のような syscall は要らない。**

#### 動いているアニメーションを壊さないこと

移し替えは全部を捨てるのではなく、**`pending` に区間がある `(オブジェクト, パラメータ)`
についてだけ** `active` を置き換える。

> **不変条件**: `start_` によって状態が変わるのは、
> 今回 `add_` が触れた `(オブジェクト, パラメータ)` に限られる。

同じパラメータを再び駆動すれば前のアニメーションは打ち切られ、
触れていないパラメータ・触れていないオブジェクトは走り続ける。

`start_` で走行中のものが**全部**止まるようにしないのは、
背景の 10 秒パンの最中にキャラクターが 0.3 秒跳ねただけで
パンが死ぬのは明らかに困るからである。

### パラメータごとに、いつでも活性な区間は 1 つ

`add_` された区間は `(オブジェクト, パラメータ)` ごとに `after` の順に並ぶ。

**ある区間は、同じパラメータの次の区間が始まった時点で終わる。**
この 1 つの規則で全部説明がつく。

- `duration` が尽きた `once` 系はそのまま値を保つ (次が来るまで)
- 終端を持たない周期系は、次の区間が来るまで続く
- 区間が重なっていれば、後の区間が前を打ち切る

「複数の連続した transition をエンジンがスケジューリングし、
後の transition の開始時点で前の loop 系を打ち切る」という想定どおりに動く。
loop / once という区分を API に持たせる必要は無く、
**振る舞いは kind ごとに決まる**ままでよい。

### 基準値 (baseline) は区間が活性になった瞬間に捉える

`sin` の「現在の値を基準に」も、`linear` の始点も、同じ規則で扱える。

**区間が活性になった瞬間のそのパラメータの値を基準値として捉え、区間の間保持する。**

`after = 0` の区間ではこれは `start_` の瞬間の値に一致する。
遅れて始まる区間では活性化の瞬間の値になり、こちらのほうが素直に動く。

```
add(x, linear, 500, 0,    1000)   // 1 秒かけて x=500 へ
add(x, sin,     20, 1000,  400)   // その後 x=500 を中心に揺れる
```

基準値を `start_` 時点で固定すると、後者は元の位置を中心に揺れることになり、
1 秒後に飛ぶ。活性化時に捉えれば `500` を中心に揺れる。

保持のためのスロットは新設しなくてよい。**オブジェクトが持つパラメータの現在値
そのもの**を、区間の活性化時にコピーするだけである。

周期系は「基準値からの偏差」を出すものとして定義する
(`value = baseline + A · wave(t)`)。区間が終われば偏差は消え、値は基準値に戻る。

### `none`

`kind = none` は「この時刻でこのパラメータのアニメーションを終わらせ、
**その時点の落ち着いた値で固定する**」。`value` と `duration` は使わない。

「落ち着いた値」なので、周期系が乗せていた偏差はここで消える
(前節のとおり周期系は値そのものを動かしていない)。
一度限りの遷移を途中で切った場合は、切った瞬間の値がそのまま残る。

これで loop を止められる。

```
add(x, linear, 500, 0,    2000)   // 2 秒かけて右へ
add(y, sin,     20, 0,     600)   // 周期 600ms で上下に揺れながら
add(y, none,     0, 2000,    0)   // 移動が終わると同時に揺れも終わる
start()
```

同じパラメータに単振動と移動を重ねる合成は、これでは表現できない。
そこまでは今回狙わない。上のように**パラメータを分ければ十分**である。

なお周期系を `none` で切ると、位相が 0 でなければ偏差の分だけ値が跳ぶ。
綺麗に終わらせたければ `after` を周期の整数倍にするか、
`none` の代わりに基準値へ戻す `once` 系の区間を置く。
これは std のラッパが計算してやればよい。

### cast のまとめ流し —「同一ターン」は誤り

前回「同一ターン内の cast をまとめて 1 回の postMessage にできる」と書いたが、
**そこに言う「ターン」は存在しない。** 訂正する。

`worker.ts` は wasm のエントリポイントを**同期に呼ぶ**
(`(entrypoint)(null)`)。ゲームは最初から最後までこの 1 回の同期呼び出しの中で走り、
ブロッキング syscall では `Atomics.wait` でスレッドごと止まる。
Worker がイベントループに帰る瞬間はゲームの実行中に存在しない。
したがってマイクロタスクやターン境界での flush はできない。

正しい flush 点は次の 3 つ (+ 保険) である。

| 契機                                 | 理由                               |
| ------------------------------------ | ---------------------------------- |
| `call` (ブロッキング syscall) の直前 | 順序を保つため。必ず要る           |
| `start_transitions`                  | **発火はまとまって届く必要がある** |
| `exit`                               | 取りこぼさないため                 |
| 溜まった件数が上限を超えたとき       | 一度も止まらないシーンへの保険     |

`start_` で流すのが要点である。バッチが 1 通のメッセージになるので、
**メインスレッドはバッチの途中でフレームを描けない。**
これは速度の話ではなく、発火の原子性が構造として保証されるという話である。

速度そのものは正直たいした問題ではない (1 アニメーションあたり数回の postMessage は
数 µs のオーダーで、これが毎フレーム起きるわけでもない)。
それでも入れる価値があるのは、上の原子性と、
**API の粒度を輸送コストのために歪めなくてよくなる**ことにある。
案 1 も案 3 も、突き詰めればこのまとめ流しを API の形で手作業でやっているにすぎない。

TypeScript ターゲットでは中断しない syscall はただの関数呼び出しなので、
この話は wasm 側の輸送路の中だけで閉じる。API には現れない。

## エンジン側の実装

### オブジェクトレジストリ

**biwa 側のパラメータを正 (source of truth) とし、Pixi へは毎フレーム射影する。**
スプライトに直接値を書くのは続かない。以下が全部ずれているからである。

| biwa                           | Pixi                     |
| ------------------------------ | ------------------------ |
| 原点は canvas 中央、y は上が正 | 左上、y は下が正         |
| 回転の中心は画像の中心         | `anchor` 次第 (既定 0,0) |
| `alpha` 0–255                  | `alpha` 0–1              |
| `theta` 度                     | `rotation` ラジアン      |
| `w` / `h` が負 = 未指定        | 常に具体的な値           |

```ts
interface CanvasObject {
  id: number;
  view: Container; // Sprite / AnimatedSprite / video
  natural: { w: number; h: number } | null; // ロード完了まで null
  value: Float64Array; // param ごとの現在値 (biwa の座標系)
  base: Float64Array; // 活性な区間が捉えた基準値
  active: Segment[][]; // param ごとの、走っている区間列
  pending: Segment[][]; // param ごとの、次の start_ を待つ区間列
  dirty: boolean;
}
```

`start_` の実体は、`pending[param]` が空でない `param` についてだけ
`active[param] = pending[param]` と置いて `pending` を空にすることである。
空の `param` には触らない。これが前節の不変条件そのものになる。

射影で注意する点:

- `anchor = 0.5` にする。中心原点 + 中心回転の規約に一致する
- **y を反転する分、`rotation` の符号も反転する。** しないと「正 = 反時計回り」が破れる
- `w` / `h` が負のときは `natural` を使う。片方だけ正ならアスペクトを保つ

### 非同期ロードとの噛み合わせ

いまの `api/image.ts` はスプライトが `.then` の中でしか存在しない。
`create` が積んで返る以上、**ロード完了前に届いた `add_`/`start_` を受ける先が無い。**

1. `create_object` は**同期にオブジェクトを作る**。
   `Texture.EMPTY` の `Sprite` を `visible = false` で登録し、パラメータを初期化して返す
2. ロードが解決したらテクスチャを差し替え、`natural` を埋め、`visible = true` にする
3. その時点で、走っている `w` / `h` の区間の基準値を `natural` で解決し直す

`Texture.EMPTY` はサイズ 0 なので、**`sprite.width` の setter を通すと scale が
Infinity になる。** ロード前はサイズを触らないこと。

ポップインが気になる用途には、別途ブロッキングの `preload(path)` を用意する。

### Ticker は 1 本

現状 `api/image.ts` はスプライトごとに `ticker.add` していて、**一度も `remove` していない。**
オブジェクトを消してもコールバックとクロージャが残る。

**`TransitionRunner` が `ticker.add` を 1 つだけ持ち**、全オブジェクトの区間を進める。

- 上のリークが消える
- 処理順が決定的になる
- スキップ・オート・ポーズが 1 箇所の時間スケールで効く

### エンジン時計

`performance.now()` ではなく **`ticker.deltaMS` を積んだ自前の時計**で区間を進める。
`after` / `duration` はこの時計の上の値とする。これで次が全部同じ操作になる。

| やりたいこと       | 操作                                              |
| ------------------ | ------------------------------------------------- |
| ポーズ             | 時計を進めない                                    |
| オート / 早送り    | 時計に係数を掛ける                                |
| 演出のスキップ     | 対象の区間の終端まで時計を飛ばす                  |
| ロード時の記録再生 | 時計を終端まで飛ばし、値を確定させる (描画しない) |

### 消してよいもの

`CommandQueue.ts` / `types/Command.ts` / `commands/` / `engine/tween.ts` は
互いに参照し合うだけの島になっていて、syscall の経路からは到達しなかった
(`CommandQueue` 時代の名残)。この設計を入れる時点でまとめて消した。

## スケジューリング

### 2 つのスケジューラを混ぜない

|              | 何を並べるか           | 誰が動かすか                  |
| ------------ | ---------------------- | ----------------------------- |
| presentation | 遷移・遅延・周期       | エンジン時計 (Ticker)         |
| scene        | シーンが進むか止まるか | kernel (`next()` / `Atomics`) |

テキストがクリック待ちで止まっていても、canvas のアニメーションは当然止まらない。
両者が交わるのは次の 2 点だけである。

### テキストと同期する演出 / しない演出

**これを分ける手段が今の案に無い**、というのが残っていた問題である。
`start_transitions` に印を 1 つ持たせて解く。

```
start_transitions(sync = 0)   // 独立。テキストとは無関係に走る
start_transitions(sync = 1)   // 同期。テキストの進行と結びつく
```

`sync` が付いたバッチだけが、次の 2 つの対象になる。

- **クリック**: 進行中の `sync` バッチがあるとき、クリックはまずそれを完了させて消費される。
  テキストを進めるにはもう一度クリックが要る
- **`await_transitions()`**: `sync` バッチが全部終わるまでシーンを止める

これで 3 通りが 2 つのプリミティブから組める。

| したいこと                                         | 書き方                             |
| -------------------------------------------------- | ---------------------------------- |
| 走らせっぱなし (背景のパン、常時のゆらぎ)          | `start(0)`                         |
| テキストは進むが、次のクリックで先に演出が完了する | `start(1)`                         |
| 演出が終わるまでシーンを進めない                   | `start(1)` → `await_transitions()` |

判定は `once` 系の区間だけを見る。**終端を持たない周期系は「完了しない」ものとして
数えない** ので、`sync` バッチにゆらぎが混じっていても `await` が固まることはない。
スキップはバッチの時計を「そのバッチの最後の `once` 区間の終端」まで進める操作なので、
`none` で終わらせてある周期系はその過程で正しく終わる。

std の高水準 API は用途ごとにどちらを使うかを決めておけばよい
(キャラクターの登場は `sync`、背景のループは独立、など)。

### セーブ・ロードとの制約

`docs/execution-model.md` の「残っていること」に書いたとおり、
**中断しない syscall は今エンジンの API を直接叩いていて、再生中に副作用を止められない。**
メディア系はまさにこれで、しかも canvas の状態は `Game` に入っていないため
**再生でしか復元できない**。したがって設計上こう縛られる。

1. **メディア系の cast も kernel を経由させる** (`yield` は要らない。登録するだけでよい)
2. **オブジェクト id は決定的に採番する。**
   `alloc` の Worker 側カウンタはこれを満たす。
   テクスチャのロード完了順など非決定的なものに依存させてはいけない
3. **早送り中は区間を終値で確定させる** (エンジン時計を飛ばす)

すぐやることではないが、**id の採番方法と cast の経路は後から変えにくい**ので、
今の判断に含めておく。

## 番号の定義

`param` と `kind` の番号は**両ターゲットで共有される**。
wasm 側の std は `.wat` に整数を直書きすることになるので、
一覧が 1 箇所にあることが特に重要になる。

`src/engine/api/transition.ts` に置き、TypeScript の native からは import させ、
wasm の std へは書き写す。写し間違いが黙って通らないよう、
**範囲外の `param` / `kind` はエンジンが名指しでエラーにする**
(`worker.ts` が未知の import 名で叱っているのと同じ方針)。

`kind` は once 系と周期系で値の範囲を離す。振る舞いは kind ごとに決まるので
API 上の区分ではないが、読んで分かるようにしておく。

| param |         | kind (once) |               | kind (周期) |            |
| ----- | ------- | ----------- | ------------- | ----------- | ---------- |
| 0     | `x`     | 0           | `none`        | 16          | `sin`      |
| 1     | `y`     | 1           | `linear`      | 17          | `triangle` |
| 2     | `w`     | 2           | `ease_in`     | 18          | `square`   |
| 3     | `h`     | 3           | `ease_out`    | 19          | `saw`      |
| 4     | `alpha` | 4           | `ease_in_out` |             |            |
| 5     | `theta` | 5           | `ease_out_in` |             |            |

`value` の単位はパラメータの単位そのもの (canvas の単位 / 0–255 / 度)。
周期系では振幅、`duration` は周期を表す。

`EaseIn` は「ゆっくり始まり速く終わる」、`EaseOut` はその逆とした。
`docs/media-syscall-wasm.md` の記述とは反対になっているが、
CSS をはじめ既存のツールがすべてこの意味で使っているので、
名前から受ける印象が食い違わないほうを採った。
入れ替えるなら `api/transition.ts` の `curveAt` の 2 行で済む。

## 残っていること

- **std のラッパ**。今 `base_engine` にあるのは番号を直接渡す生の層である。
  `Param` / `Curve` に名前を付け、キャラクターの登場や退場を組み立てる層は別に要る
- **TypeScript ターゲットのブロッキング syscall**。
  `await_transitions` / `sleep` は当面 wasm 専用である。
  コンパイラが `yield` を置くのは今のところ novel statement の展開先だけで、
  任意の関数呼び出しを中断させる手段が無い
- **`theta` の分解能**。目標値が整数度だと、ごく緩やかな回転で刻みが見える
  (補間そのものは内部 float なので中間は滑らか)。必要になったら 1/10 度などに変える
- **将来の回転 2 軸**。`param` を足すだけで入る
- **`w` / `h` を「未指定」に戻す遷移**。今の `value` は絶対値しか表せない
- **音**。時間軸を持つ点は同じだが canvas 上のオブジェクトではないので、
  別の syscall 群になる。エンジン時計は共有したい
- **`preload`**。ポップインを避けたい場面用のブロッキング syscall。
  今はテクスチャが読めるまでオブジェクトが見えないので、
  この間に走らせたフェードインは見えないまま終わる
- **動画と GIF**。`create_object` は拡張子で分ける前提で書いてあるが、
  今あるのは静止画のバックエンドだけである
- **記録再生**。中断しない syscall はまだ kernel を通っていない
